## 4. 설계 — 가장 중요한 결정 세 가지 (2:15~4:00)

**[화면]** 구성도 (휴대폰 → Next.js 서버 → Supabase / Gemini API), 계층 그림

> 구조는 Next.js 하나로 화면과 서버를 함께 만들고, DB와 로그인은 Supabase를 썼습니다. 세 명이 5주에 끝내야 해서 서버를 따로 두지 않았습니다.

**[화면]** "재고는 묶음 단위 + 기한 빠른 것부터 차감(FEFO)" 그림: 양파 묶음 A(기한 11/20)·B(11/25)

> 첫 번째 결정은 재고를 재료 총량이 아니라 **들어온 묶음 단위**로 관리한 것입니다. 그래야 묶음마다 기한을 알 수 있고, 판매하면 기한이 빠른 묶음부터 줄일 수 있습니다. 기한이 지난 묶음은 차감에서 빼고 폐기하도록 안내합니다.
> 차감은 계산과 반영을 나눴습니다. 어떤 묶음에서 얼마를 뺄지는 TypeScript 순수 함수가 계산하고, 반영은 DB 함수 하나가 한 트랜잭션으로 합니다. 그래서 계산은 DB 없이 테스트할 수 있고, 반영은 일부만 되는 일이 없습니다.

**[화면]** Adapter 패턴 그림: 추천 기능 → `AiClient` → Gemini / Claude / 고정 응답

> 두 번째는 AI 호출을 **Adapter 패턴**으로 감싼 것입니다. 추천 기능은 `AiClient`라는 인터페이스만 알고, 실제 모델은 어댑터가 부릅니다.
> 이 결정이 실제로 효과가 있었습니다. 13주차에 비용 문제로 AI를 Claude에서 Google Gemini 무료 등급으로 바꿨는데, 어댑터 파일 하나를 추가하고 선택 한 줄만 바꿨습니다. 추천 로직, 결과 검증, 화면은 한 줄도 바뀌지 않았습니다.

**[화면]** Strategy 패턴 그림: 추천 기준 칩(유통기한 우선 / 원가 우선 / 인기 우선) → 같은 검증

> 세 번째는 추천 기준을 **Strategy 패턴**으로 나눈 것입니다. 기준마다 재료 우선순위만 다르고, AI 결과를 재고와 대조하는 검증은 하나로 모았습니다. 기준을 추가해도 검증 코드는 건드리지 않습니다. 실제로 같은 AI 응답을 세 기준으로 처리하면 결과가 같은지 테스트로 확인했습니다.

> 테스트 계획 177건과 하나하나 대조해서, 테스트가 계획의 기대값을 전부 확인하는지 읽었습니다. 127건 통과, 실패 0건이고, 나머지는 실제 AI 20회 평가나 실기기 측정처럼 아직 못 한 것이라 통과로 치지 않고 남겨 두었습니다.
> 재고 계산은 모든 기대값을 손으로 먼저 계산해 적었습니다. 예를 들어 AI가 제안한 특선의 원가 4,350원은 두부 2모 1,800원, 돼지고기 150g 2,250원, 대파·양파 각 150원을 더한 값과 같습니다.
> 마지막 주에는 일부러 깨 보는 보안 점검을 했습니다. AI 사용 횟수 기록을 직접 지워 하루 한도를 우회하는 경로, 같은 날 마감과 주문이 동시에 와서 재고가 두 번 줄어드는 경로를 실제로 재현했고, 고치기 전 코드에서 테스트가 실패하는 것을 먼저 확인한 뒤 막았습니다.

| 질문 | 답 |
|---|---|
| AI가 틀린 재료를 말하면? | 재료는 서버가 실제 재고와 대조해 보유·부족·미등록으로 표시하고, AI가 준 수량·원가는 쓰지 않는다. 저장은 사용자가 확인한 뒤에만 된다 (BR-04) |

| 두 기기에서 동시에 판매를 마감하면? | 같은 날짜는 한 번만 마감된다. 다른 날짜끼리 같은 묶음을 동시에 차감하면 DB가 묶음을 잠그고 잔량을 다시 확인해서, 바뀌었으면 최신 재고로 한 번 다시 계획한다 |
| 다른 가게 데이터가 보이지 않나? | DB 행 단위 보안(RLS)으로 매장을 격리했고, 서버는 화면이 보낸 매장 ID를 믿지 않고 로그인 세션에서 매장을 구한다. 다른 계정 접근 테스트로 확인했다 |
| 왜 Next.js 하나로 했나? | 3명·5주라 배포·인증 연동 비용을 줄였다. 서버 로직은 Server Action과 DB 함수로 나눠 계층은 유지했다 |
| 기한이 지난 재료는? | 판매 차감에서 빼고 대시보드에 "지남"으로 따로 보여 주며, 폐기 기록으로 바로 연결된다 |
