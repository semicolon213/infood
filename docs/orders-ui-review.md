# 4.3a 발주 목록 화면 검토 기록

- 담당: 성윤우 · 2026-11-17
- 기준: develop의 4.3b 병합 시점 `e5c2c87`(PR #53), SRS FR-ORD-01~05·UC-09, API 10장, 디자인 4.6·7장
- 브랜치: `feature/4.3a-orders-ui`
- 상태: 화면 구현·독립 QA 후속 보완 후 김형균 리뷰 대기. 실제 발주 조회·액션에 계약 그대로 연결했다. 실제 DB 통합 검증 완료를 의미하지 않는다.

## 구현

| 화면 | 내용 |
|---|---|
| `/orders` | 저장 목록·상태·품목 수·메모, 기간 조회와 역전 날짜 검증, 빈 목록 |
| `/orders/new` | 서버 권장 초안, 사용 가능·적정·미입고 수량 표시, 품목 추가·삭제, 기본 단위 입력, 발주일·메모 |
| `/orders/[id]` | 품목·수량·메모, 복사와 수동 복사 복구, 상태 변경·삭제 확인 |
| `/orders/[id]/edit` | 작성중만 수정. 발주완료·입고완료는 직접 URL로 들어와도 수정 차단 |
| 공통 | 로딩, 조회 실패 재시도, 잘못된 ID·없는 목록, 중복 제출 잠금, 필드 오류·실패 시 입력 보존 |

조회는 서버 컴포넌트에서 `lib/queries/orders`·`ingredients`를 호출한다. 변경은 `saveOrder`·`setOrderStatus`·`deleteOrder` 계약을 사용한다. 서버·계약·계산·DB·공통 UI는 수정하지 않았다. 권장 수량은 화면에서 계산하지 않고, 표시·복사는 기존 `formatQty`·`formatOrderText`를 사용한다. `qty ≤ 0` 행은 입력 순서대로 서버에 보내 오류 경로를 유지하며, 서버가 저장 시 제외한다.

입고완료 확인창에는 입고 등록을 먼저 확인하도록 안내하고, 상태 표시 자체가 재고를 늘리지 않으며 되돌릴 수 없음을 설명한다. 자동 거래처 전송·자동 입고·발주 불러오기 확장은 추가하지 않았다.

## 검증 방법

기존 작업 폴더의 `test-results/worktrees`가 전역 TypeScript 검사에 포함되는 영향을 피하려고, 최신 develop의 깨끗한 소스 복사본에 4.3a 변경만 적용해 검사한다. 새 의존성은 추가하지 않았다. pnpm 실행 파일이 없어 동일 package scripts를 `npm.cmd run`으로 실행하며 lockfile은 바꾸지 않는다.

- `npm.cmd run lint`
- `npm.cmd run typecheck`
- 최초 검증: Vitest 200건 통과·77건 건너뜀, 입력 보조 12건·375×812 화면 검사 9묶음.
- QA 후속 및 4.3b 동기화 후 `npm.cmd test`: 205건 통과·90건 건너뜀. 로컬 Supabase 의존 검사 미실행.
- 입력 보조 16건: 기존 12건에 선택 불가 행의 추가 한도, 제출 시 표시값 읽기, 연결되지 않은 서버 오류 안내, 잘못된 날짜의 필드 연결을 추가했다.
- `node tests/e2e/orders/check.mjs`: 17묶음 통과. 기존 검사에 M1·M2, 실제 fixture 상태 변경 후 재조회, 원값·근삿값 병기, 서버 필드 오류, 품목 오류 포커스, DOM 표시값 제출, 날짜 오류 연결, 360·1024 화면, g·ml 복사와 삭제 NOT_FOUND 복구를 추가했다. 결과와 스크린샷은 `test-results/orders-ui-check/`에 생성.

브라우저 보조 검사는 운영 파일을 변경하지 않고 `test-results/orders-browser-app/` 복사본의 조회·액션만 로컬 HTTP fixture로 바꾼다. 실제 Supabase·RLS·RPC·영속화, 실제 AI 평가는 이 검사의 범위가 아니다. 인증 만료는 `ActionResult(UNAUTHORIZED)` 복구만 검사하며 실제 proxy 리다이렉트 경로는 별도 확인이 필요하다.

## 서버 연동·리뷰 시 남은 확인

1. **4.3b 연결:** PR #53의 실제 조회·액션을 작업 브랜치에 fast-forward로 반영했다. 화면은 동일한 import·DTO·액션 시그니처를 사용한다. 신규 저장·상세 재조회·수정·삭제·상태 변경의 실제 DB 영속화·RLS·RPC는 로컬 Supabase에서 IT-ORD·E2E-07 재검증이 필요하다. `STUB_ORDERS`·`STUB_ORDER_DRAFT`는 테스트용으로 보존한다.
2. **복사 ea 표기:** `30개`와 `30ea`는 `10_TEST_PLAN.md` 10.2의 합의 대기 사항이다. 담당자 안내에 따라 IT-ORD-08 보조 판정은 g·ml만 확인한다. `lib/stock/order.ts`는 변경하지 않았다.
3. **인증·응답 유실:** 실제 proxy 로그인 이동과 네트워크 응답 유실 후 수동 재저장 중복은 서버 연동 시 확인한다. 현재 계약에 멱등성 보장이 없으므로 자동 재시도하지 않는다.
4. 김형균 지정 리뷰와 PR 병합 전에는 `11_TASK.md`를 완료 처리하지 않는다.
5. 검증 중 Next.js 16.4.3이 보안 업데이트 권고를 표시했다. 원본 의존성·설정은 이번 범위에서 변경하지 않았다. 자동 브라우저 검사의 복사본에서만 `experimental.agentUpgrade: false`로 대화형 안내를 끄고 검사했다. 보안 업데이트는 별도 작업으로 검토해야 한다.

독립 QA 지적별 대응과 보류 근거는 [QA 후속 기록](orders-ui-qa-fixes.md)을 참고한다.
