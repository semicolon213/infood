# 3.2a 독립 QA 후속 수정

기준: 사용자가 제공한 독립 QA 보고서 D-1~D-8. 원본 자료는 `test-results/menus-independent-qa/`에 보존한다. 이번 수정은 성윤우의 메뉴 화면·테스트 범위다.

## 항목별 처리

| 항목 | 처리 | 남은 범위 |
|---|---|---|
| D-1 재료 stub과 실제 DB ID 불일치 | 화면 수정 없음 | 임지섭의 3.1b 이후 실제 Supabase로 재검증 |
| D-2 인증 만료 시 복구 경로 없음 | 액션 전송 예외에도 새 창 로그인 링크 제공. 원래 창의 입력·확인창을 유지하고 로그인 후 재시도 가능 | 실제 매직링크·Supabase 세션 갱신 검증. proxy/액션의 일관된 인증 응답은 임지섭 확인 |
| D-3 소수 4자리 이상 수량·부분 저장 | 화면에서 소수 셋째 자리까지 검증, 입력값을 반올림하지 않고 필드 오류로 차단 | 공유 Qty 정밀도 계약(임지섭), 메뉴·레시피 원자 저장(김형균)은 미수정 |
| D-4 다른 행 오류 해제 | 변경한 필드만 해제. 행 삭제 시 남은 오류 경로를 새 인덱스로 이동, 해소된 중복 오류만 제거 | 회귀 검사로 확인 |
| D-5 첫 오류 포커스 | 객체 키 순서 대신 현재 폼의 DOM 순서상 첫 오류 입력에 포커스 | 회귀 검사로 확인 |
| D-6 판매가 int 상한 | 화면에서 2,147,483,647원 상한·필드 안내 적용 | 공유 계약·서버 검증(임지섭·김형균)은 미수정 |
| D-7 지수 표기 | 화면 문자열 파싱에서 지수·진법 표기 거부 | 서버 숫자 계약은 유지 |
| D-8 요청 기록·fixture 한계 | 요청 본문 깊은 복사, 저장 데이터와 참조 분리, 재료의 매장·활성·ID 조건 적용, 일부 DB 범위·정밀도 제약 모사. 1024px 상세·등록·수정도 점검 | 실제 PostgreSQL/Auth/RLS와 동등한 구현은 아님 |

로그인 복구는 인증 전용 오류 응답이 오지 않는 전송 예외에도 제공한다. 네트워크 실패만으로 인증 만료를 단정하지 않는다. 새 창에서 로그인하도록 해 원래 폼의 초안을 유지하며, 클라이언트의 새 DB 조회·직접 변경이나 공유 인증 코드 변경은 추가하지 않았다.

정밀도·판매가 상한은 현재 DB의 저장 범위를 지키기 위한 **화면 방어**다. 공유 API·계약·서버 액션은 소유자 합의 전까지 유지한다. 다른 클라이언트의 직접 액션 호출까지 막는 서버 검증 및 DB 장애에서의 원자성은 해결되지 않았다.

## 검증 기록

Windows Node 24에서 lint 오류 0건(외부 QA 자료의 기존 경고 1건), typecheck·build 통과. Vitest 107건 통과·DB 관련 24건 건너뜀, Playwright 보조 브라우저 19개 흐름 통과. 375×812 및 1024px의 목록·상세·등록·수정 화면을 확인했다.

최종 실행 결과는 `menus-ui-review.md`와 `test-results/menus-ui-check/result.json`을 함께 확인한다. 보조 fixture 검사와 실제 Supabase 통합 검증을 구분한다.

추가 회귀 범위:

- D-3·D-6·D-7의 수량 정밀도·판매가 상한·지수 표기 입력 및 서버 전송 차단
- D-4의 행별 오류 보존·삭제 후 인덱스 재배치·해소된 중복 안내
- D-5의 화면 순서상 첫 오류 포커스
- D-2의 실제 proxy 401→리다이렉트 상황, 로그인 새 창 이동, 원래 입력 유지, 인증 복구를 모의한 재시도와 비활성화 재시도
- D-8의 매장·활성·ID별 서버 거부, 후속 수정 후에도 보존되는 최초 요청 기록

실제 Supabase 통합, iOS/Android 실기기, 지정 리뷰어 승인·병합은 남아 있다.
