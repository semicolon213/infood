# 보안 1번 후속 QA (WBS 4.4c)

2026-11-24. develop `5e3a720` 기준의 **검토용 초안**이다. 직접 변경 차단은 PR #82가 담당하고, 이 변경은 실행 경로 강화와 일반 사용자 보안 회귀 검사를 추가한다. 선행 PR #79·#82 병합과 서버·테스트 지정 리뷰어 임지섭의 승인이 필요하다. 4.4 전체 완료나 운영 적용을 뜻하지 않는다.

## 변경과 적용 순서

- `0010_rpc_search_path_hardening.sql`: API 역할의 재고 쓰기 권한과 변경 함수의 실행 모드를 확인하고 `PUBLIC`의 보호 테이블 쓰기·public 스키마 CREATE를 회수한다. 네 공개 RPC와 매장 확인·내부 차감 함수에 `public, pg_temp`를 설정한다.
- `ai-sales-rls.test.ts`: 로컬 Supabase의 일반 사용자·새 매장으로 직접 변경 거부, 실패 후 기록·재고 유지, 정상 RPC·취소, 주문 재전송, 매장 격리·익명 차단, AI 동시 한도를 검사한다. 날짜는 `todayKST()`의 상대값이다. 실제 AI와 service role을 사용하지 않는다.
- 판매 재입력 PR #74도 채택하면 **0007 → 0008(#79) → 0009(#82) → 0010** 순서다. 0010을 먼저 적용하는 것은 선행 조건 오류로 중단한다. develop 대상 CI도 선행 마이그레이션이 없으면 통과할 수 없으므로 초안 상태를 유지한다.
- 이후 함수 재정의는 실행 모드·안전한 search_path·실행 권한을 보존해야 한다. 적용된 과거 마이그레이션 파일의 수정으로 해결하지 않는다.

## QA에서 재현한 기존 문제

| 항목 | 실제 결과 | 담당자 확인·추천 |
|---|---|---|
| 매장 삭제·재생성으로 한도 재사용 | 같은 사용자가 한도 2를 소진한 뒤 자기 매장을 삭제·재생성하면 같은 날짜 카운터가 다시 1로 증가한다. 동시 다중 매장은 owner_id UNIQUE가 거부한다. | 매장 삭제 요구사항을 확정한다. 지원하지 않으면 직접 DELETE 회수를 추천하며, 지원하면 매장 삭제와 분리한 비용 제한이 필요하다. NFR-12는 매장별 한도이므로 계정별 정책을 임의로 추가하지 않는다. |
| 마감·주문 동시 차감 | 동일 매장·동일 날짜의 마감 1건과 주문 1건이 상대 기록 검사를 모두 통과하면 둘 다 성공하고 재고가 1000→800으로 줄어든다(각 100). | 두 RPC가 상대 테이블을 검사하기 전에 같은 매장·판매일의 트랜잭션 잠금을 얻도록 별도 수정하고 두 실행 순서를 검증해야 한다. |
| 0007의 뒤늦은 재적용 | `record_daily_sales`의 search_path가 public으로 돌아간다. 확인한 PR #74의 0007은 이미 definer여서 실행 모드는 유지된다. | 배포 순서를 고정하고 함수 옵션 검사로 회귀를 확인한다. |

두 반례는 기존 함수·매장 정책에서 발생하며 이 PR에서 해결했다고 주장하지 않는다. 재고 행 잠금은 잔량을 보호하지만 마감·주문 경로의 상호 배제를 보장하지 않는다. 이 PR에 매장 수명 정책이나 판매 RPC 본문 변경을 섞지 않았다.

## 검증 범위

기존 후보는 develop `7b8bd6e`에 PR #79(0008) 및 선택적으로 PR #74(0007)를 적용해 실제 로컬 Supabase에서 검증했다. 보안 6/6, 기본 구성 340/340, 판매 재입력 포함 구성 343/343이었고 실패·건너뜀은 없었다. 이 수치는 서로 다른 구성이므로 합산하지 않으며 현재 PR의 테스트 수와도 구분한다. 원본 결과·후보·설정·타입 파일 9개의 SHA-256과 바이트 길이를 후속 QA에서 대조했다.

후속 QA는 일반 사용자 Auth·REST 요청으로 위 두 반례를 재현했다. 동시 판매 검사에만 외부 세션의 테스트용 묶음 행 잠금 장벽을 사용했으며 앱·RPC에 테스트 장치를 넣지 않았다. 같은 매장 AI 요청 12회/한도 2에서는 성공 2·초과 거부 10·저장 count=2였다. public의 쓰기 가능한 뷰는 없고 private은 REST 노출 스키마에 포함되지 않는다. 기존 is_my_store는 처음부터 definer와 SET 옵션이 있어 이번 변경으로 인라인 성능 회귀가 생겼다는 근거는 없다.

이번 PR은 develop `5e3a720`과 선행 PR #79·#82를 격리 복사본에서 결합해 검증했다. 원본 작업 폴더나 운영 DB는 변경하지 않았다.

| 구성·검사 | 결과 |
|---|---|
| develop + #79 + #82 + 이번 변경 | 345 PASS / 0 FAIL / 0 SKIP |
| 위 구성 + #74 소스·0007 | 348 PASS / 0 FAIL / 0 SKIP |
| 새 보안 회귀 검사 | 두 구성 모두 7/7 PASS (전체 수에 포함) |

| DB 타입 재생성 | 두 구성 모두 기존 타입과 줄바꿈 정규화 후 동일 |
| 함수·테이블 권한 | 6개 함수의 definer·search_path 확인, 2개 API 역할×6개 테이블×4개 쓰기 권한 모두 없음 |

검증 프로젝트는 `infood-security-pr-20261124`, API 56321·DB 56322의 로컬 Supabase다. 실제 AI·클라우드 DB는 사용하지 않았다. [검증 요약과 원본 해시](logs/security-1-20261124/verification.json)를 함께 남긴다. 로컬 결합 구성의 통과를 아직 선행 변경이 없는 develop 대상 CI 통과로 표시하지 않는다.

## 리뷰 시 확인

- DB·서버 소유 파일의 사용자 요청에 따른 검토용 변경이다. 소유자 임지섭의 승인 전 병합하지 않는다.
- PR #79의 기존 대시보드 테스트는 과거 stock_movements fixture 준비에만 로컬 service role을 사용한다. 앱·새 보안 테스트에서는 사용하지 않으며 이 선행 예외는 담당자가 별도 검토한다.
- 매장 삭제 정책과 동시 차감 수정의 작업 담당·일정을 확정한다.
- 선행 PR 병합 후 develop에 맞춰 문서 충돌·마이그레이션 순서·CI를 다시 확인한다.
