# 3.7a 사용·폐기 기록 화면 검토

- 담당: 성윤우 / 지정 화면 리뷰어: 김형균
- 요구사항: FR-USE-03~05, FR-DASH-02, UC-06
- 작업 브랜치: `feature/3.7a-usage-waste-ui` (develop `f903200`에서 분기)
- 상태: 화면·기존 계약 연결 구현. 3.1b·3.7b 실제 DB 연동 및 지정 PR 검토·병합 전까지 `[~]` 유지.

## 구현

| 화면·흐름 | 동작 |
|---|---|
| `/waste` 사용 탭 | 서버의 KST 오늘을 기본 사용일로 표시. 재료·기본 단위 수량·100자 메모를 여러 행으로 입력하고 `recordUsage` 호출 |
| 폐기 탭 | 재료와 잔량 있는 입고 묶음을 선택. 묶음별 입고일·기한·잔량·경과 상태, 폐기량·사유·메모 입력 후 `recordWaste` 호출 |
| `/waste?lotId=...` | 기존 재료 상세의 링크로 진입. 해당 묶음만 선택하고 경과 묶음일 때에만 잔량 전체·기한 경과 사유를 미리 채움 |
| 잘못된/없는 묶음 링크 | 다른 묶음을 자동 선택하지 않고 안내. 사용자가 재료·묶음을 명시적으로 다시 선택 |
| 저장 결과 | 사용은 서버의 부족분 표시, 폐기는 서버가 돌려준 남은 양 표시. 성공 후 새 기록을 누를 때까지 재전송 잠금 |
| 기록 조회 | 기본 최근 7일, 최대 31일 기간·사용/폐기 필터를 URL에 반영. 메모·폐기 사유·부족 기록, 빈 결과·조회 실패 구분 |

- 조회는 서버 페이지에서 기존 `getIngredients`, `getIngredient`, `getStockHistory`를 사용한다. 클라이언트 테이블 변경과 새 서버 계약은 없다.
- 숫자는 문자열에서 파싱한 뒤 공유 Zod 입력으로 검증한다. 빈 수량·0·음수·소수 4자리 이상·지수 표기·수량 상한·폐기 잔량 초과를 입력 아래에 안내한다. 사용일 미래 날짜를 막는다.
- 날짜 계산·기한 배지는 기존 `lib/stock/expiry`의 `addDays`, `daysLeft`를 사용한다. 단위 환산·FEFO·차감·부족량은 화면에서 계산하지 않는다. 사용은 기본 단위로 입력하며 계약의 `unit` 생략 규칙을 따른다.
- 사용 행의 중복 재료는 공유 계약에 따라 허용한다. 같은 재료를 합치는 서버 처리는 3.7b 범위다.
- 행 추가·재료 변경은 다른 오류를 유지한다. 삭제 후에는 남은 오류를 새 인덱스로 연결한다. DOM 순서상 첫 오류로 포커스를 이동한다.
- 탭을 전환해도 각 폼의 입력을 유지한다. 저장 중 잠금, 결과의 중복 제출 방지, `STOCK_CONFLICT` 안내·새로고침을 제공한다.
- 통신 예외는 저장 실패로 단정하지 않고 기록을 먼저 확인하도록 안내한다. 인증 만료가 proxy 리다이렉트로 전달되는 경우에도 새 창 로그인 링크를 제공해 원래 창의 입력을 보존한다.
- 44px 이상 터치 영역, 16px 입력, 안전 영역을 반영한 저장 바와 키보드 탭 조작을 적용한다. 기한 표시는 매장 기준 권장 기한 안내를 포함한다.
- 독립 QA D-1~D-7 후속 수정: 직접 묶음 선택의 입력 유지, 결과 스크롤·포커스, 새 창 기록 확인, 부족 문구·메모 보존·NOT_FOUND 복구, 실제 고정 레이아웃 회귀 검사. [상세 처리](waste-ui-qa-fixes.md) 참고.

## 변경 범위

- `src/app/(main)/waste/`: 서버 조회 페이지·로딩·오류 복구
- `src/components/waste/`: 사용·폐기 폼, 입력 검증·상태, 결과·기록 조회
- `tests/e2e/waste/check.mjs`: 모바일·데스크톱 화면 보조 점검
- `docs/11_TASK.md`, `docs/logs/ai-usage.md`, 이 검토 문서

액션·조회·공유 계약·DB·계산 함수·공통 UI 변경과 의존성 추가는 없다. 기존 `.env.example` 수정은 이번 작업에 포함하지 않는다.

## 검증

- lint 오류·경고 0건, `next typegen` + `tsc --noEmit` 통과, 프로덕션 build 통과.
- Vitest **109건 통과·24건 건너뜀**. 이번 화면 입력·오류 상태 보조 검사 **13건** 포함. 건너뛴 24건은 로컬 Supabase가 필요한 DB·메뉴 통합 검사다.
- 현재 작업 폴더의 실제 앱을 띄워 Playwright Chromium에서 **16개 흐름 통과**. 375×812와 1024px, 한국어·Asia/Seoul, 가로 넘침·44px 터치 영역·키보드 탭을 확인했다.
- [사용 입력](images/waste-usage-375.png), [묶음 선택·자동 채움](images/waste-preselected-375.png), [부족 결과](images/waste-shortage-375.png), [폐기 결과](images/waste-result-375.png)를 직접 열어 확인했다.
- 화면 이미지는 실제 고정 헤더·저장 바·하단 탭과 현재 스크롤을 유지한 뷰포트 촬영본으로 교체했다. [직접 묶음 선택의 입력 유지](images/waste-manual-375.png)도 기록했다. 결과의 포커스·가시성은 촬영 전후 좌표 검사로 확인한다.

재현: `node tests/e2e/waste/check.mjs` (별도 dev 서버 불필요). `test-results/waste-ui-check/`에 결과 JSON·서버 로그·이미지를 생성한다. 초기 컴파일 대기는 기능 검사와 구분하며 NFR 응답 시간 측정에 사용하지 않는다.

### 검증 환경 분리

기존 작업 폴더의 전체 타입 검사는 이전 메뉴 QA 임시 파일이 이 브랜치에 없는 메뉴 모듈을 참조하고, 이전 브랜치의 `.next/dev/types`도 남아 있어 실패했다. 해당 자료를 삭제·수정하지 않고 git 추적 파일과 이번 미추적 소스를 `test-results/waste-validation-0a90b43b/`에 복사해 lint·typecheck·test·build를 실행했다. 환경변수 파일·이전 임시 산출물은 복사하지 않았고 설치된 같은 node_modules를 연결했다. 임시 Next 설정의 Turbopack root만 의존성 연결을 위해 조정했다.

앱·컴포넌트의 검증 대상 11개 파일은 원본과 복사본의 SHA-256이 모두 같음을 확인했다(`test-results/waste-ui-check/source-hashes.json`). 브라우저 최종 검증은 원래 작업 폴더의 앱에서 수행했다. pnpm이 PATH에 없어 설치된 Node 24로 각 package script의 같은 실행 파일을 호출했다.

3. 네트워크 실패 시 입력 유지·기록 확인 안내·재시도

5. 재료 상세에서 정확한 경과 묶음으로 진입, 잔량 전체·사유 자동 채움

독립 QA 후속 회귀 6건: 결과 포커스·고정 바 사이 가시성, 받침 있는 재료명 문구, 수동 묶음 선택의 수량·사유 보존, 재료 변경의 메모 보존, NOT_FOUND 새로고침, 인증 만료 중 새 창 기록 확인·원본 입력 유지.

인증·매장만 로컬 HTTP fixture를 사용하고 재료·사용·폐기·기록은 프로젝트의 기존 stub을 호출했다. 부족분·`STOCK_CONFLICT`·`NOT_FOUND` 복구는 **액션 응답만 브라우저에서 모의**했다. 이 점검을 실제 DB·RPC·FEFO·전체 E2E-04·정식 IT-USE-06~09 통과로 집계하지 않는다. 실제 AI·운영 DB·외부 계정은 사용하지 않았다.

## 서버 담당자·리뷰 확인 사항

1. **3.1b·3.7b 연동:** 현재 재료·묶음·이력 조회와 사용·폐기 액션은 고정 stub이다. 성공 응답이 실제 차감·이력 추가·영속화를 의미하는지는 검증하지 않았다. 실제 RPC·매장 격리와 전체 E2E-04는 3.7b 이후 별도 검증한다.
2. **부족·충돌 처리:** 사용 stub은 항상 빈 부족분을 반환한다. 부족 경고와 `STOCK_CONFLICT`는 브라우저의 액션 응답만 모의해 표시·복구를 확인한다. 실제 부족량·FEFO·경합 처리는 검증하지 않는다.
3. **조회 비용:** 기존 계약에 묶음 ID 전용/일괄 조회가 없어 재료 목록 후 재료 수만큼 상세를 서버에서 병렬 조회한다. 실제 DB 연동 후 조회 성능을 확인하고 필요하면 임지섭과 일괄 조회 계약을 합의해야 한다.
4. **정밀도:** 현재 공유 Qty에는 소수 자릿수 제한이 없다. 화면은 `numeric(12,3)` 저장 범위를 지키지만 직접 액션 호출까지 막는 검증은 3.7b 담당자 확인이 필요하다.
5. **전송 결과 불명확:** 서버가 반영한 뒤 응답만 유실되는 경우의 중복 방지는 현재 계약으로 보장할 수 없다. 화면은 자동 재시도하지 않고 기록 확인을 안내한다. 요청 식별자·멱등성 보장은 서버 담당자 합의 대상이다.
6. **남은 검증:** 실제 Supabase/Auth/RLS·재고 트랜잭션, 실제 매직링크 로그인, iOS/Android 실기기, 지정 리뷰어 승인·PR 병합.
7. **미실행 화면 경로:** 고정 조회 stub으로 재료 0개·전체 재료 조회 실패·기록 조회 실패 상태를 브라우저에서 만들지는 않았다. 해당 안내·재시도 코드는 정적으로 확인했으며 실제 서버 장애 모의 검증은 3.7b 이후 보완한다.
