## 1. 목적과 범위

- **목적:** 재고 수량과 유통기한이 정확하게 계산·반영되는지, AI 추천이 재고 DB와 어긋나지 않는지, AI가 실패해도 재고 관리가 계속 동작하는지 검증한다.
- **필수 범위:** SRS의 P0 요구사항(F-01~F-05와 재료·메뉴·로그인), 비즈니스 규칙 BR-01~06, 비기능 요구사항 NFR-01~12, 데이터 요구사항 DR-01~03. P0의 정상·예외 경로를 모두 검증한다.
- **선택 범위:** P1·P2는 1.2의 채택 조건에 따라 실행한다. 미채택 선택 기능을 필수 기능의 통과 조건에 섞지 않는다. FR-USE-06의 재입력을 채택하지 않아도 중복 마감 거부는 필수다.
- **범위 밖:** 부하 테스트, Claude API 자체의 정확성, 바코드·공공 API·라벨 날짜 인식·축산물 이력·PWA(요구사항에서 제외됨)

### 2.1 원칙
- **도메인 로직은 실제 DB 없이 테스트한다.** 오늘 날짜(`today`)와 기준일은 항상 인자로 주입한다. 테스트에서 시스템 시계를 쓰지 않는다.
- AI는 `AI_MOCK=1`의 `MockAdapter` 고정 응답으로 테스트한다. 실제 모델 호출은 AI 평가(7장)에서만 한다.
- 테스트 이름에 이 문서의 ID를 붙인다 (예: `UT-FEFO-05: 부족분 반환`).
- 아래 표의 날짜는 모두 2026년이며, 별도 표시가 없으면 오늘 = 11/03이다.

### 2.2 증거 수준과 판정

- **계획·구현·실행·통과를 구분한다.** 이 문서에 ID가 있거나 같은 ID의 테스트 파일이 있어도 통과를 뜻하지 않는다. 4.4에서 실행한 커밋·환경·로그와 함께 판정한다.
- **단위:** 순수 함수·Zod·SDK 목. **화면 stub/HTTP fixture/응답 모의:** 화면 동작·요청 DTO·오류 복구만 입증한다. 고정 stub의 성공 응답은 실제 잔량 변경·영속성·트랜잭션·RLS를 입증하지 않는다.
- **DB:** 실제 로컬 Supabase에 일반 사용자로 접근한 RPC·RLS 증거. **통합:** 실제 Auth·조회·서버 액션·DB를 연결하고 AI만 목으로 바꾼 증거. **전체 E2E:** 이 통합 환경에서 브라우저 흐름을 끝까지 실행한 증거. UI 보조 스크립트만으로 E2E-02·04 전체를 통과 처리하지 않는다.
- 실제 AI 품질은 7장 평가, 실기기 호환성은 NFT-12의 별도 증거로만 판정한다. 한 수준의 통과를 다른 수준의 통과로 올리지 않는다.
- `PASS`=해당 기대 결과 전부 충족, `FAIL`=실제 결과 불일치, `BLOCKED`=선행 구현·환경 부족, `NOT RUN`=미실행, `SKIP`=러너가 건너뜀, `N/A`=미채택 선택 기능. `SKIP`·`BLOCKED`는 `PASS`가 아니며 필수 항목의 종료 기준을 충족하지 않는다.

### 2.3 환경·데이터·재현 절차

1. **실행 기준 고정:** 커밋 SHA, Node 22·pnpm 버전, OS·브라우저·뷰포트, `AI_MOCK`, DB/fixture 구분을 기록한다. 설치는 `pnpm install --frozen-lockfile`, 자동 테스트는 실제 AI 키 없이 `AI_MOCK=1`로 한다. 장애 평가만 `AI_MOCK=fail`을 쓴다.
2. **DB 준비:** 격리된 로컬 Supabase에서 `supabase start` 후 필요 시 `supabase db reset`으로 마이그레이션·시드를 적용한다. reset은 해당 테스트 DB에만 한다. 사용자 A/B를 일반 가입·로그인으로 만들고 각각 별도 매장을 소유하게 한다. 공개 키+사용자 세션으로 접근하며 service role·운영 데이터는 쓰지 않는다.
3. **날짜:** 단위 함수와 기준일 인자를 받는 RPC는 `today=2026-11-03` 또는 테스트별 기준일을 명시적으로 주입한다. 서버·브라우저 통합은 서버의 `todayKST()`를 기준일 T로 기록하고 아래 날짜를 T 기준 상대 일수로 옮긴다. 앱에 임의의 오늘 입력을 추가하지 않는다. KST 자정 경계는 통제 가능한 테스트 시계에서 별도 검증한다. 오래된 시드 날짜를 현재 임박 데이터로 간주하지 않는다.
4. **독립 상태:** 아래는 공통 fixture 설계이며 현재 `seed.sql`에 모두 존재한다는 뜻이 아니다. 각 테스트는 필요한 데이터를 입고 RPC 등 정식 경로로 준비하거나, 제약 검증용 격리 fixture로 준비한다. 실제로 생성된 ID를 이후 요청에 쓴다. 고정 stub UUID와 실제 시드 UUID를 혼용하지 않는다.
5. **실행·확인:** 호출 전 잔량·행 수 스냅샷 → 입력·동작 → 응답·화면 → 관련 묶음·업무 기록·이력 재조회 순으로 확인한다. 실패·동시성 케이스는 성공한 부분만 남지 않았는지도 비교한다. 독립 케이스마다 새 매장/재료 또는 초기 fixture를 사용하고 기존 이력을 수정·삭제해 되돌리지 않는다.

| 공통 재료 양파(g) | 입고일 | 유통기한 (T=11/03) | 초기 잔량 | 판정 |
|---|---|---|---|---|
| X | 10/30 | 11/02 (T−1) | 500g | 경과, FEFO에서 제외 |
| A | 11/01 | 11/04 (T+1) | 500g | 임박 D-1, FEFO 첫 순서 |
| B | 11/02 | 11/06 (T+3) | 300g | 임박 D-3, FEFO 두 번째 |
| C | 11/02 | 11/07 (T+4) | 200g | 정상 D-4, A·B 다음 FEFO 순서 |

사용 가능=1000g, 경과=500g, 총잔량=1500g. 최소=1200g, 적정=2000g. 발주 계산 케이스에서만 `ordered` 400g을 추가하면 권장량=600g이다. 메뉴는 양파 100g/인분(판매 7개→700g, 12개→사용 1000g·부족 200g), 다품목 검증에는 두부 1ea/인분과 별도 재고를 추가한다. 3장의 개별 입력이 다르면 해당 표를 우선한다.

X·A·B·C는 유통기한 추적 재료의 정식 입고 화면·액션으로 만들 수 있도록 입고일·기한을 명시한다. C의 null 기한 전제는 제거했다. null 기한 정렬은 UT-FEFO-04·UT-STAT-05에서 별도 검증한다. IT-ING-06의 null 혼합 묶음은 DB가 허용하는 상태를 `receive_stock` 직접 호출로 준비하는 조회 fixture이며, 해당 상태를 정식 입고 액션으로 생성했다고 주장하지 않는다. 추적 제외 재료의 정식 입고는 기한 null·근거 없음도 따로 확인한다.

충돌 재시도 IT는 조회·계획과 RPC 사이를 동기화하는 테스트 장치로 다른 세션의 변경을 커밋시킨다(4.1). DB-11은 두 요청의 합계가 실제 잔량보다 큰 고정 계획으로 한쪽 실패를 보장하는 병렬 실행도 인정한다. 성공/충돌 수·최종 잔량·업무 기록·이력이 기대값과 일치해야 하며, 병렬 요청을 보냈다는 사실만으로 충돌 경로 통과를 판정하지 않는다. 요청·응답 증거는 깊은 복사로 보관하고 fixture도 매장·활성 여부·ID 필터를 적용한다.

### 4.1 충돌·다품목 원자성의 재현 조건

- **준비:** 같은 매장의 서로 다른 재료 P/Q에 입고일 T−2·기한 T+3의 500g 묶음을 하나씩 입고한다. P/Q는 처리 순서의 이름이다. 반환 ID를 조회해 DB-09는 ingredient_id 순서, DB-11은 lot_id 순서에서 P가 앞에 오도록 매핑하고 입력·계획을 계약 순서로 정렬한다. `stock_lots.remaining` 직접 update 대신 다른 세션의 폐기 RPC로 잔량을 바꾼다.
- **DB-09:** 오래된 계획 P=100·Q=300을 보관하고 Q=250 폐기를 먼저 커밋한다. 이 시점의 P=500·Q=250과 기록·이력 스냅샷을 기준으로 실패 요청의 효과를 비교한다. P 처리 후 Q에서 300>250 충돌이 나도록 하고, P 차감·P/Q 사용 기록·사용 이력 모두 없는지 별도 일반 세션에서 확인한다. Q의 타 요청 폐기까지 되돌아가야 한다고 기대하지 않는다.
- **DB-11:** 양쪽 판매에 P 100g·Q 300g이 필요한 메뉴를 사용하고, 날짜는 미마감 T−1/T로 둬 중복 날짜 `CONFLICT`를 배제한다. Q 합계 600>500이므로 RPC의 고정 계획에는 재계획을 끼우지 않는다. 실패한 요청에서 P가 먼저 처리되는 조건을 유지하고, 최종 P가 300g이면 실패 요청의 부분 반영을 검출한다(정답 400g).
- **IT-USE-05·10:** 실제 서버 액션·조회·Supabase RPC를 연결한다. 테스트 장치는 계획 완료 직후 실행을 잠시 멈추는 지점만 제공하고 응답·에러를 목으로 만들지 않는다. 최초 계획 P 100g·Q 300g 뒤 다른 세션이 Q 250g을 폐기하면 첫 RPC는 충돌한다. 서버는 1회 재계획해 P 100g·Q 250g·부족 Q 50g을 저장한다. 최종 P=400g·Q=0g, 업무 기록 1세트(판매: 마감 1·판매 1, 사용: P/Q 사용 기록 2·Q short_qty=50), 실패 시도 기록 0건, RPC 시도 정확히 2회를 확인한다.
- **재시도 한도:** 독립 초기 상태에서 재시도 계획 Q 250g 직후 추가 폐기 100g도 커밋시키는 변형을 같은 IT에 포함한다. 두 번째 RPC도 충돌하면 최종 `STOCK_CONFLICT`, 시도 2회에서 종료, P=500g·Q=150g, 이 액션의 업무 기록·사용 이력 0건이다. 타 요청 폐기 이력 2건만 보존한다.
- **증거:** 요청별 계획·실행 순서, 경쟁 요청 커밋, RPC 시도 횟수, 모든 관련 테이블 전후 스냅샷을 남긴다. 이 동기화 장치의 구현·실DB 검증은 임지섭 검토·4.4 실행 대상이며 준비 전에는 `BLOCKED`다. 목 기반 분기 검사는 별도 보조 증거로만 기록한다.

## 7. AI 평가 (`pnpm eval:recommend`)

### 7.1 데이터
- `eval/recommend/`에 준비할 가상 데이터: 재료 30종, 메뉴 15개, 판매 14일로 만든 재고 상황 시나리오 5개(정상 혼합, 경과만 보유, 재고 부족, 미등록 재료 유도, 단가·판매량 순위 차이). 각 시나리오에 기준일·매장·묶음·정답(보유/부족/미등록)을 고정한다. 아직 평가 데이터가 구현됐다는 뜻은 아니다.
- 기준 3개(expiry·cost·popularity)를 섞어 시나리오당 4회, **총 20회** 실행한다.
- 기준별 횟수를 사전에 고정하고(예: expiry 10회, cost 5회, popularity 5회), 요청·응답·재고 스냅샷·후처리 결과를 연결한다. 정답은 AI 출력이나 검증 대상 후처리 코드로 생성하지 않고 손계산·DB 스냅샷으로 교차 확인한다.
- 각 요청을 AI 생성 성공(`ok:true`, `data.fallback=false`), 규칙 기반 대체(`ok:true`, `data.fallback=true`), 최종 오류(`ok:false`)로 분류한다. 최소 품질 표본은 **실제 AI 생성 성공 20건**이며 시나리오별 4건·기준별 사전 분포도 충족해야 한다. 이는 SRS의 20회 AI 검증을 위한 표본 조건이며 서비스 성공률을 새로 정하는 요구사항은 아니다. 기본 20회에서 표본이 모자라면 충족을 주장하지 않는다.

### 7.3 실행
- 실제 모델을 호출하므로 비용이 든다. 프롬프트·스키마·Strategy를 바꿀 때와 13주 측정(WBS 4.4) 때만 실행한다.
- 결과는 `eval/results/{날짜}-recommend.md`로 저장하고, 결과 표를 PR과 AI 활용 검증 보고서(12.3)에 첨부한다.
- 3.9 문서 작성·자동 테스트에서는 실행하지 않는다. 4.4에서 도구·데이터·비용 범위를 준비한 뒤 실제 평가한다. 모든 시도의 요청 수·대체·오류·지연은 보존하고, AI 품질 지표의 분모에서는 대체·최종 오류를 분리한다. AI 재료 언급이 0개이면 일치율은 100% 대신 산출 불가다.
- 일치율 오류가 하나라도 관측되면 `FAIL`이다. 오류가 없어도 AI 생성 표본 20건·분포 미달이면 NFR-03은 `BLOCKED`(표본 미달)이며 성공으로 집계하지 않는다. 예를 들어 20회 전부 대체이면 대체율 100%, AI 표본 0건으로 품질은 산출 불가다. 성공 16·대체 3·오류 1이면 AI 품질은 16건에서만 부분 집계하고 표본 미달을 기록한다.
- 부족한 표본을 채우려고 자동으로 추가 유료 호출하지 않는다. 재측정은 비용 범위를 정한 별도 실행 회차로 고정하고 이전 실패·대체 기록도 함께 보고한다. 20개 요청 시간의 P95는 정렬한 19번째 값(nearest rank)이며, 다른 표본 수이면 ceil(0.95×표본 수) 순위를 쓴다.

### 8.1 사용성 과업 시간 측정 절차 (NFR-04)
1. **대상:** 팀원이 아닌 사용자 3명 (같은 수업 다른 팀 학생 가능). 사전 연습 없이 1분 화면 소개만 한다.
2. **준비:** 시드 데이터가 들어간 매장, 실기기(스마트폰) 사용, 화면 녹화 켬.
3. **과업 A:** 입고 화면 진입 후 지정 재료 1품목(수량·단위·금액) 입고 완료까지 시간.
4. **과업 B:** 판매 마감 화면 진입 후 메뉴 10개 수량 입력·저장까지 시간.
5. **기록:** 사람별 시간, 실수·도움 요청 횟수, 한 줄 의견을 12.1 결과표 형식으로 남긴다.
6. **판정:** 3명 모두 기준 이내면 통과. 1명이라도 넘으면 결함(심각도 3)으로 등록하고 화면을 고친 뒤 다시 측정한다.

| IT-USE-05·10 | 목으로 `STOCK_CONFLICT`를 반환하는 분기 검사만으로 실제 재시도·원자성을 입증하지 못함 | 실제 조회·DB 연결, 4.1의 경쟁 세션 커밋·RPC 2회·실패 기록 부재와 재충돌 한도 확인 |

`check-plan.mjs`의 자동 PASS는 ID 존재·범위·표 열 수·추적 행 등 **구조 점검**에 한정한다. 기대값·요구사항 대응의 의미가 맞다는 증거가 아니다. 독립 QA의 의미 변이 4건이 모두 구조 검사를 통과한 한계는 보존한다. 계약·fixture 손계산·누락 여부는 근거 문서와 사람이 대조해 별도 기록하며, 이 보완 문서도 임지섭 검토·독립 재검토를 통과한 것으로 간주하지 않는다.

## 12. 산출물 양식

### 12.1 테스트 결과표 (⑥, WBS 4.4)

결과 문서 머리에 대상 커밋·기능 PR, 실행일·실행자, Node/pnpm·OS·브라우저, DB·마이그레이션·fixture 버전, 기준일/KST, `AI_MOCK`·실제 AI 여부, 명령·환경 준비 방법을 적는다. 비밀 값은 기록하지 않는다. 다음 행은 작성 예시이며 실행 결과가 아니다.

| 테스트 ID | 요구사항 | 증거 수준 | 입력·초기 상태 | 기대 결과 | 실제 결과 | 판정 | 증거·결함 |
|---|---|---|---|---|---|---|---|
| UT-FEFO-09 | BR-02 | 단위 | (작성: 기준일·묶음) | 경과 A 제외, B에서 300g | (실행 후 작성) | NOT RUN | (로그·Issue 링크) |

결과표 아래에 수준별 전체·PASS·FAIL·BLOCKED·NOT RUN·SKIP·N/A 개수를 적고 합계가 전체와 일치하는지 확인한다. 테스트 러너의 실행 수와 계획 케이스 수가 다르면 대응 관계를 설명한다. 차단 항목은 담당·의존 작업·재개 조건, 실패는 결함·수정 PR·재실행 커밋과 결과를 연결한다. 스크린샷만으로 DB 영속성 통과를 판정하지 않는다. 로그·DTO·스크린샷은 같은 실행 ID로 묶고 이전 실행 증거를 덮어쓰지 않는다.
