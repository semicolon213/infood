## 💡 왜 만들었나

소규모 음식점은 식재료 재고를 감각에 의존해 관리합니다. 그래서 유통기한이 지나 재료를 버리고, 떨어진 재료는 급하게 다시 삽니다. 재고 기록이 판매·메뉴와 연결되지 않기 때문입니다.

**"입고하고 판매만 기록하면, 무엇을 먼저 팔고 무엇을 주문할지 알려 준다."**

## ✨ 주요 기능

| ID | 기능 | 설명 |
|---|---|---|
| F-01 | 📥 **입고 등록** | 품목·수량·단위·유통기한을 입력합니다. 기한을 모르면 재료별 기본 보관일수로 자동 계산합니다. |
| F-02 | 🧾 **판매·사용 차감** | 하루 판매량을 입력하면 레시피 기준으로, 직원 식사·폐기는 입력한 만큼 **기한이 빠른 묶음부터** 차감합니다. |
| F-03 | ⚠️ **임박·부족 대시보드** | D-3 이내 임박, 기한 경과, 최소 재고 미만 재료를 첫 화면에서 보여줍니다. |
| F-04 | ✨ **AI 메뉴 추천** | 임박 재료를 소진할 기존 메뉴와 특선 아이디어를 제안하고, 재료마다 실제 재고와 대조해 **보유/부족**을 표시합니다. |
| F-05 | 📝 **발주 목록** | 부족 재료의 권장 발주량을 계산해 목록을 만들고, 수정·저장·복사합니다. |
| 확장 | 📄 명세서 사진 입고 | 필수 기능 완성 후 진행. 거래명세서 사진에서 품목·수량·단가를 읽어 확인 후 입고합니다. |

## 🔥 기술적 도전과 해결

<!-- 실제로 겪은 문제·수치로 업데이트할 것. 면접에서 가장 많이 질문받는 부분 -->

### 1. AI가 틀린 값을 재고에 넣지 않게 하기
- **문제:** AI가 수량을 잘못 읽거나 존재하지 않는 재료로 메뉴를 추천할 수 있음
- **해결:** 세 단계로 막았습니다.
  - ① AI 출력을 Zod 스키마로 강제
  - ② 서버가 재료 ID·재고량·원가를 다시 검증하고 직접 계산
  - ③ 사용자 확인 없이는 DB에 반영하지 않음
- **결과:** 추천 중 검증을 통과한 비율 `{__}`%, 잘못된 입고 `{__}`건

### 2. 동시에 판매를 입력해도 재고가 꼬이지 않게 하기
- **문제:** Supabase 클라이언트는 여러 쿼리를 하나의 트랜잭션으로 묶을 수 없음
- **해결:** 역할을 둘로 나눴습니다.
  - **차감 계획**은 TypeScript 순수 함수로 만들어 테스트
  - **적용**은 Postgres 함수(RPC) 하나에서 처리: 행 잠금(`FOR UPDATE`) → 잔량 재검증 → 반영
  - 계획한 뒤 재고가 바뀌었으면 거부하고 다시 계획
- **결과:** 동시 차감 테스트에서 음수 재고 0건, 핵심 로직 테스트 커버리지 `{__}`%

### 3. 발주량을 감이 아니라 규칙으로 정하기
- **문제:** 부족 여부만 알려 주면 얼마나 주문할지는 여전히 감에 의존함
- **해결:** 기한이 지난 묶음을 뺀 **사용 가능 재고**를 기준으로 판정하고, 권장 발주량 = 적정 재고 − 사용 가능 재고로 계산(BR-05·06). 계산은 순수 함수로 분리해 경계값까지 테스트
- **결과:** 발주량 계산 테스트 `{__}`건 통과
